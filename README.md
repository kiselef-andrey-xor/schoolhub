# SchoolHub — веб-приложение для школы

Единая цифровая среда школы: **электронные приказы с подтверждением ознакомления**, **Task Manager
с несколькими исполнителями** и **планы работы на неделю** — с ролевой моделью доступа (RBAC).

| Слой | Стек |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Pydantic v2, PostgreSQL 16 (asyncpg), JWT |
| Frontend | React 18 + TypeScript, Vite, TanStack Query, React Router, CSS-токены (без UI-библиотек) |
| Аутентификация | Локальные учётки (bcrypt) **или Active Directory** — LDAP/LDAPS bind, авто-провижининг, группы AD |
| Инфраструктура | Docker Compose, nginx (reverse-proxy + статика), локальное файловое хранилище (заменяемо на S3/MinIO) |
| Развёртывание | x86-сервер **или Synology NAS (arm64)** — готовый комплект в `deploy/synology/` |
| Качество | 104 интеграционных теста (pytest + httpx/ASGI) и 151 сквозная smoke-проверка |

## 0. Установка на Synology NAS — 5 шагов

🚀 **Пошаговая инструкция: [`docs/INSTALL.md`](docs/INSTALL.md)** — обязательных настроек нет:
`SECRET_KEY` генерируется автоматически, первого Владельца вы создадите в браузере.


Скрипт соберёт образы, запустит стек и напечатает **код первоначальной настройки**.
Дальше: `http://<адрес-NAS>:8080` → ввести код → создать Владельца → добавить сотрудников.

## 2. Функциональные возможности

### 2.1 Аутентификация и RBAC

* Локальные учётные записи (bcrypt) — основной режим; **опционально** Active Directory
  (LDAP/LDAPS bind, авто-провижининг, импорт из каталога) — см. [`docs/AD-OPTIONAL.md`](docs/AD-OPTIONAL.md).
* Мастер первоначальной настройки: первый Владелец создаётся в браузере по одноразовому
  коду из журнала контейнера (или одной командой `scripts/first_owner.py`), `SECRET_KEY`
  генерируется автоматически — установка не требует ручных секретов.
* До завершения настройки весь API закрыт (`503 SETUP_REQUIRED`), кроме `/health` и `/setup/*`.
* JWT access (30 мин, только в памяти вкладки) + refresh (14 дней) в **httpOnly-cookie**
  (`SameSite=strict`, путь `/api/v1/auth`) — XSS не может ни прочитать, ни отправить его на чужой сайт.
* **Refresh-сессии отзываемы**: каждый токен хранится в БД (`refresh_sessions`) и **ротируется**
  при каждом обмене; выход, смена/сброс пароля и блокировка учётки отзывают сессии немедленно;
  повторное предъявление заменённого токена (вне 30-секундного окна для параллельных вкладок)
  трактуется как кража — семейство сессий отзывается целиком, событие пишется в аудит.
* 3 роли: `OWNER` (Владелец), `ADMIN` (Администрация), `TEACHER` (Учитель) — иерархия `TEACHER(1) < ADMIN(2) < OWNER(3)`.
* Права проверяются **двумя независимыми слоями**:
  1. **API**: зависимости `require_role(...)` выполняются до хендлера + точечные проверки в сервисах
     (например, учитель не может переназначить задачу или изменить дедлайн).
  2. **UI**: набор `capabilities` приходит с сервера в `GET /auth/me`, по нему скрываются разделы и кнопки.
     Фронтенд **не является** границей безопасности — при подмене клиента API вернёт 403.
* Защита от эскалации: нельзя выдать роль своего уровня или выше (кроме Владельца), нельзя разжаловать
  или заблокировать самого себя, в школе всегда остаётся хотя бы один активный Владелец.
* Сквозной журнал событий (`audit_log`): кто, что, когда, с какого IP и какие поля изменились (diff).

### 2.2 Модуль «Приказы»

* Просмотр документов **PDF** (инлайн-превью в браузере) и **DOCX** (скачивание; при наличии LibreOffice
  на сервере — автоматическая конвертация в PDF для инлайн-просмотра).
* Жизненный цикл: `Черновик → Опубликован → Архив` (переходы валидируются, архив read-only).
* Версионирование файлов: каждая загрузка — новая версия, история и sha256-контроль суммы сохраняются.
* Фильтрация: полнотекстовый поиск, тип приказа, статус, период по дате, «есть неподписанные»,
  «ждут моей подписи»; пагинация; синхронизация фильтров с URL.
* Статус **«Ознакомлен»**: явное подтверждение с фиксацией времени, IP и User-Agent (аналог подписи
  в бумажном листе ознакомления), повторное подтверждение невозможно (409).
* Лист ознакомления: круг подписчиков — **все сотрудники или выбранный список** (задаётся ещё
  в черновике, меняется и после публикации — подписи ознакомившихся сохраняются), прогресс,
  список неподписавших, экспорт в CSV для отчётности.
* Валидация загрузки: только PDF/DOCX/DOC, до 25 МБ, отказ на пустой файл и чужой MIME-тип;
  **содержимое сверяется с сигнатурой формата** (`%PDF-`, OOXML-пакет, OLE2) — подделанный
  `Content-Type` не спасает; защита от path traversal (`is_relative_to`, content-addressed пути).

### 2.3 Task Manager

* Создание задач, **несколько исполнителей**, дедлайн, приоритет (`LOW/NORMAL/HIGH/URGENT`).
* У каждого исполнителя — **своя отметка «выполнено»**: первая отметка переводит задачу
  в «В работе», когда отметки поставили все — задача автоматически закрывается;
  снятие отметки возвращает задачу в работу.
* **Вложения задач**: офисные файлы, изображения, архивы (до 25 МБ, sha256),
  скачивание участниками, удаление — загрузившим/постановщиком/администрацией.
* Статусы: **Новая → В работе → Выполнена**, плюс **Просрочена**.
* **«Просрочена» — вычисляемое состояние**, а не значение в БД: `status != DONE AND deadline < now`.
  Оно наступает само по себе, поэтому хранить его нельзя (данные устаревали бы без cron'а).
  Сервер считает его в SQL-предикатах и отдаёт полями `effective_status` / `is_overdue` / `days_left`.
* Видимость: учитель — только свои задачи (и 403 на чужие), админ/владелец — все.
* Учитель может менять статус и описание своей задачи, но **не** исполнителей, дедлайн и приоритет.
* State machine переходов статусов, история изменений, комментарии (только для участников задачи),
  уведомления исполнителям и постановщику (назначение, отметки, закрытие).
* Отчёт по просрочкам в разрезе исполнителей (`GET /tasks/overdue-report`).

### 2.4 Модуль «План работы на неделю»

* Электронный аналог школьного Word-документа «План работы ДД.ММ–ДД.ММ»:
  дежурный класс и классный руководитель, блоки **«В течение месяца»** и **«В течение недели»**,
  таблица мероприятий по дням (пн–сб): мероприятие, время, место, ответственные.
* **Ответственные — учётки сотрудников**: при публикации все они получают уведомление;
  на дашборде и в списке планов видно «моих пунктов: N».
* Жизненный цикл: **Черновик → Опубликован → Архив** (один план на неделю, дубли запрещены).
* Редактор повторяет структуру документа; неделя пересчитывается автоматически (пн–сб).
* Просмотр — «бумажный» вид как в Word, **печать/PDF** одной кнопкой (печатается только документ).
* Права: создают/редактируют/публикуют — Владелец и Администрация; видят опубликованные
  и архив — все сотрудники.

## 3. Архитектура

```
┌──────────────┐   HTTPS    ┌───────────────────────┐   asyncpg   ┌──────────────┐
│  React SPA   │ ─────────► │  nginx (статика +     │             │ PostgreSQL 16│
│  (Vite, TS)  │  /api/*    │  reverse-proxy /api)  │             └──────────────┘
└──────────────┘            └───────────┬───────────┘
                                        │
                            ┌───────────▼───────────┐        ┌───────────────────┐
                            │ FastAPI (uvicorn)     │        │ File storage      │
                            │  api/    → маршруты   │───────►│  локальная ФС      │
                            │  services/ → бизнес   │        │  (S3/MinIO-ready) │
                            │  models/  → ORM       │        └───────────────────┘
                            │  security → RBAC/JWT  │
                            └───────────────────────┘
```

**Слои backend'а** (зависимости направлены внутрь, бизнес-логика не знает про HTTP):

```
app/
├── api/          # HTTP-слой: маршруты, RBAC-зависимости, сериализация ответов
├── services/     # бизнес-логика: приказы, задачи, уведомления, аудит, хранилище, документы
├── models/       # SQLAlchemy ORM (таблицы и связи)
├── schemas/      # Pydantic-контракты запросов/ответов
├── security.py   # JWT, хеширование паролей, require_role(), get_current_user
├── capabilities.py  # матрица прав «роль → возможности» (единый источник для API и UI)
├── enums.py      # доменные справочники и state machine статусов
├── types.py      # портируемые типы колонок (UUID, Enum→VARCHAR)
├── dbutils.py    # переносимый регистронезависимый поиск (ILIKE ↔ SQLite)
└── main.py       # фабрика приложения, middleware, обработчики ошибок
```

Подробности — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) (модель данных, ключевые решения, ADR).
Полный контракт API — в [`docs/API.md`](docs/API.md) и в Swagger (`/docs`).

## 7. Продуктивный контур (чек-лист)

1. **Секреты**: `SECRET_KEY` из vault/secret-manager, `DEBUG=false`, `APP_ENV=prod`.
   Файл `backend/storage/secret_key` не должен попадать в репозиторий (закрыт `.gitignore`);
   если ключ когда-либо утекал — удалите его (или том `secrets`) и перезапустите backend:
   новый ключ сгенерируется автоматически, все сессии будут сброшены.
2. **Миграции**: схема ведётся **Alembic** (`backend/alembic/`), при старте применяется сама
   (`AUTO_MIGRATE=true`); новые изменения — `make revision m="…"`. Ручной прогон: `alembic upgrade head`.
3. **Хранилище**: заменить `LocalFileStorage` на S3/MinIO (протокол `FileStorage` уже описан),
   bucket приватный, раздача через подписанные URL.
4. **HTTPS**: TLS-терминация на nginx/ingress, `Strict-Transport-Security`; включите
   `COOKIE_SECURE=true` (cookie начнёт передаваться только по HTTPS).
5. **Refresh-токены**: уже httpOnly + `SameSite=strict` + серверные сессии с ротацией и отзывом;
   при горизонтальном масштабировании deny-list не нужен — сессии лежат в PostgreSQL.
6. **Лимиты**: rate-limit на `/auth/login` встроен (попытки/минуту на IP+логин), неудачные попытки в аудите.
7. **Наблюдаемость**: structured-логи (JSON), `/health` + `/ready`, метрики Prometheus, трейсинг (OpenTelemetry).
8. **Резервные копии**: ежедневный `pg_dump` + снапшоты хранилища документов; проверка восстановления.
9. **Превью DOCX**: `apt-get install -y libreoffice-writer --no-install-recommends fonts-dejavu-core` —
   конвертер подхватится автоматически (`app/services/documents.py`).
10. **CI**: `pytest`, `smoke_test.py`, `tsc --noEmit`, `npm run build`, линтеры (ruff/eslint), scan образов (trivy).

## 8. Что расширено сверх ТЗ

* Авторизация через Active Directory: LDAP/LDAPS bind, авто-провижининг учётных записей,
  синхронизация атрибутов и групп, маппинг групп на роли, импорт сотрудников из каталога,
  панель диагностики подключения к DC.
* Готовый комплект развёртывания на Synology NAS (arm64): compose с лимитами памяти,
  скрипт подготовки домена (PowerShell), ежедневный `pg_dump` с ротацией и контрольными
  суммами, скрипт диагностики, конфигурация DSM Reverse Proxy.

* Уведомления (in-app) о новых приказах, назначении задач, смене статусов и комментариях.
* Журнал событий с diff'ом изменений и выгрузка листа ознакомления в CSV.
* Версионирование документов, sha256-контроль целостности, история статусов задачи.
* Дашборд с ролевой семантикой (личный контур у учителя, глобальный у администрации).
* Канбан-доска задач, отчёт по просрочкам, справочники и матрица прав через API.
